Jitera Fork Blueprint

  1. Edit the sourceChange files directly in the repo. GitHub shows the real code, so review is easy.
  2. Keep patchesfork/dev save records every change as a patch, used only for syncing.
  3. Store the checkpointfork/CHECKPOINT holds the upstream commit hash our changes are based on.
  4. SyncBack to the checkpoint, remove our changes, take the latest upstream, re-apply the patches, fix any that fail.

4

How sync works

Weekly, or on each upstream release. The result is one merge commit on a sync/ branch, reviewed as a PR.

Sequence: sync
Sync saysMeaningDo this
✓ appliedUpstream didn’t touch our linesNothing
= kept oursA file in fork/OWNED; sync kept our versionIf it says upstream changed it, run the printed git diff and copy anything useful
✗ CONFLICTUpstream changed the same lines, or added a file we also addedIn the file, keep upstream’s new code (<<<<<<< ours) and re-apply our change (>>>>>>> theirs). Then fork/dev sync --continue
✗ FAILEDThe file moved or was deleted upstreamRedo our change where the code lives now, git add new files, then fork/dev sync --continue

Merge sync PRs with Create a merge commit. A squash or rebase drops the checkpoint commit from history, and fork/dev verify will fail. Git remembers each conflict fix (rerere) for the next sync.

5

How build works

The code in git already contains our changes. The build checks that the patches match, then builds.

Sequence: build and release

Locally: fork/dev build (wheel) or fork/dev build binary.
